# 技术说明

目标程序：Plain Craft Launcher 2（VB.NET / WPF / .NET Framework 4.8，单文件发布）。

## 1. 为什么不能"改常量重编译"

PCL 源码里限制开关是 `Public Const RestrictMcDownload As Boolean = True`。
VB 编译器会把常量**内联到调用点**并做**常量折叠**：

- `If RestrictMcDownload Then ... Else ...` 只剩 True 分支；
- `If RestrictMcDownload Then Return` 之后的语句被视为不可达，**整段被删除**。

所以发布版二进制里既没有可翻转的 `ldc.i4.1`，也没有"解锁后本该走的那条路径"。
只能自己把该走的分支"接"上去。

## 2. 补丁一：下载解锁（核心）

`PCL.PageDownloadInstall.LoaderInit` 里被折叠成：

```il
ldarg.0 ; callvirt get_LoadMinecraft
ldarg.0 ; callvirt get_PanLoad
ldarg.0 ; callvirt get_PanAllBack
ldnull
ldstr   "关闭下载"                 <-- 锚点 A：假任务名
ldsfld  $IR3-3 / brfalse / ... / newobj Action::.ctor   <-- VB 静态 lambda 缓存样板
ldnull ; ldc.i4.2
newobj  LoaderTask2::.ctor(String, Action1, Func1, ThreadPriority)
ldarg.0 ; ldftn LoadMinecraft_OnFinish ; newobj Action::.ctor
ldnull ; ldc.i4.1
call    PageLoaderInit[String, DlClientListResult](...)
ret
```

把 `ldstr "关闭下载"` 到 `newobj LoaderTask::.ctor` 的整段（整段参数求值，
合计只压入 1 个值）替换为：

```il
ldsfld PCL.ModDownload::DlClientListLoader
```

余下字节用 `nop` 填满，长度不变；栈行为等价（1 个 LoaderTask(Of String, DlClientListResult)）。
目标字段类型与 `PageLoaderInit` 形参完全匹配，已用反射核对。

**锚点 B（兜底）**：若"关闭下载"改名，则先在程序集里找出所有"含有形如
`不再提供 / 无法提供 / 停止提供 / 暂停提供 … 下载` 的 ldstr" 的方法（即抛限制异常的
lambda），再在 `LoaderInit` 中找引用它的 `ldftn/ldtoken`，向前回溯到最近的 `ldstr`
（任务名）、向后找到最近的 `newobj LoaderTask...`，同样替换该区间。

## 3. 补丁二：屏蔽更新（可选）

1. `PCL.ModSecret.get_HasUpdatePermission()` —— 原实现是
   `DonationRank >= 12 OrElse PotatoFeatures.Contains("Update")`，是自动更新与手动更新的
   **公共闸门**。改为 `ldc.i4.0; ret` + nop 填充。
2. 全程序扫描 `call PCL.ModSecret::UpdateCheckByButton`（0 参数、void）→ 替换为 5×`nop`。
   覆盖：关于页按钮、设置页按钮、左侧栏、自定义事件"检查更新"。
3. 全程序扫描 `call PCL.ModSecret::UpdateReplace(...)` → 替换为"参数个数个 `pop`" + nop，
   使 `--update` 分支即使被触发也只会退出、不会替换 exe。

## 4. 补丁三：修改页版本卡片显隐（可选）

`callvirt get_CardMinecraft; ldc.i4.2 (Collapsed); callvirt set_Visibility`
→ 把 `ldc.i4.2` 改为 `ldc.i4.0`（Visible）。

## 5. 为什么是"等长字节改写"

Cecil 直接 `Write` 整个程序集需要解析所有引用程序集，而
`MeloongCore`、`PCLCS` 等私有程序集是内嵌在 exe 资源里的，实际会抛
`AssemblyResolutionException: Failed to resolve assembly 'PCLCS'`。

而全部补丁点都是**指令级、定长**的替换，因此：定位用 Cecil（只读元数据，无需解析依赖），
落盘用原始字节数组做偏移级覆盖。好处：不改 PE 头、不改 metadata、不动资源、不改文件大小。

## 6. 安全策略（失败即不写入）

- 目标方法含异常处理块（`ExceptionHandlers.Count > 0`）时，解锁补丁跳过；
- 替换区间内**不得有来自区间外的分支目标**（逐个检查 `br` / `switch` 操作数）；
- 多个修改区间不得重叠、不得越界；
- 写入前在目标目录做一次临时文件探测，失败则中止（不生成备份、不改 exe）；
- 写入后用 Cecil 重新读回并校验：解锁处必须存在 `ldsfld DlClientListLoader`、
  不得残留假任务；屏蔽更新后不得再存在相关 `call`；
- 幂等：已解锁 / 已屏蔽的文件会被识别并跳过，重复运行不会改坏文件。

## 7. 定位失败时的判定顺序

1. 找不到 `PCL.PageDownloadInstall` 或 `LoaderInit` → 报告结构不同；
2. 既无"关闭下载"也无限制文案引用 → 若已存在 `ldsfld DlClientListLoader`，
   区分"本就无限制的旧版本（如 2.13.x）"与"已打过补丁"；否则报告未找到；
3. 找到锚点但区间内含外部跳转 / 无 `LoaderTask` 构造 → 报告并**不写入**。

## 8. 补丁四：整合包安装恢复（新增 PE 段）

### 8.1 为什么这里不能沿用"等长替换"

`ModSecret.vb` 里是 `Public Const RestrictMcDownload As Boolean = True`。
`Const` 会被 VB 编译器**内联并做常量折叠**，于是：

```vb
If RestrictMcDownload Then Throw New Exception("…不再提供 MC 下载功能…")   ' ModModpack.vb:88
Select Case PackType
    Case 0 : Return InstallPackCurseForge(…)
    …
End Select
```

`Throw` 之后的所有语句都不可达，被整段删除。发布版里
`ModpackInstall(String,String,String)` 到 `throw` 就结束了——**没有派发、没有 `ret`**，
连"改成跳走"的落点都不存在，等长改写在原理上做不到。

好消息：`ModModpack` 的 12 个方法（含 7 个 `InstallPack*`）在发布版里**都还在**，
只是没人调用。所以只缺"派发"这一小段。

### 8.2 重建方法体

1. 用 Cecil 找到 3 参数的 `ModpackInstall`，在方法体里找操作数是限制文案的 `ldstr`，
   其偏移记为 `split`（2.99.0.0 上是 `0x2DA`）。
2. `[0, split)` 的原始 IL 字节**原样复制**（zip 类型识别那段，含它自己的 try/catch）。
3. 从 `split` 开始生成：

   ```
   ldloc.s V4                ; PackType
   switch  L0,L1,L2,L3,L4,L9
   Case Else（switch 的默认落点）:
        ldarg.0; ldloc.1;                          call InstallPackCompress;      stloc.0; leave END
   L0:  ldarg.0; ldloc.1; ldloc.2; ldarg.1; ldarg.2; call InstallPackCurseForge; stloc.0; leave END
   L1…L4、L9 同理（参数个数与顺序严格照源码）
   END: ldloc.0; ret
   ```

   结果变量用的是原方法里编译器留下的临时局部变量 `V0`（`LoaderCombo(Of String)`），
   所以**不需要新增局部变量签名**（也就无需扩堆）。
4. 原方法的外层 `finally`（`Archive?.Dispose()`，10 字节）整段搬到 `leave` 目标之前。
5. 异常表按新偏移重算，并把发布版里那两处"陈旧"的 `TryEnd`（编译器按删除前的布局写死）
   收敛到处理器起点：内层 finally `[0x143,0x276)`、catch `[0x6D,0x284)`、
   外层 finally `[0x27,F)`、其处理器 `[F,F+10)`。

### 8.3 放到哪里：原地扩展最后一段

新方法体比原来长，必须放到别处，但**不能移动任何既有段**：实验证明，只要改动某个段的
`VirtualAddress`（哪怕结构上完全自洽、`SizeOfImage` 也对得上），Windows 加载器就直接
`ERROR_BAD_EXE_FORMAT`，表现为“该应用无法在你的电脑上运行”；而 .NET 的托管 PE
解析器不校验这一点，所以 `Assembly.Load` 与 JIT 全都正常，直到双击启动才炸。

因此最终做法是**原地加长最后一段**（原来的 `.reloc`，2.99.0.0 上 VA `0x5B8000`、
原始数据 `0x5B5200`、原本只有 `0xC` 字节）：

- 段名改为 `.pclx`，`VirtualSize` 与 `SizeOfRawData` 扩到能容纳新方法体，特征改 `0x60000020`；
- `VirtualAddress` / `PointerToRawData` / `SizeOfImage` / 重定位目录**全部不动**；
- 内容 = 原 12 字节重定位块（原样留在最前面，重定位语义不变）+ 对齐填充 + 新方法体，
  追加写在这段尾部（文件因此只 +512 字节）；
- 只改 4 个字节的元数据：MethodDef 表里该方法的 RVA 列 → `0x5B8010`。

这样新代码落在镜像最后一页内（VA `0x5B8000`、`SizeOfImage` 仍为 `0x5BA000`），
不新增段、不移动段、不改 `SizeOfImage`，加载器无感。

### 8.4 校验

- 加载器：把产物写成临时文件后用 `LoadLibraryExW` 实际映射一次，
  `ERROR_BAD_EXE_FORMAT` 会立刻暴露——这一条是用户在真机上启动失败后才补上的。

- 回读：Cecil 重新加载，确认方法体里有指向 `InstallPack*` 的 `call`、异常表非空；
- 语义：把重建结果与"用 `RestrictMcDownload=False` 从源码编译的同版本启动器"逐条对比，
  7 个分支的调用目标、参数顺序、`leave`/`finally` 结构完全一致；
- 运行时：在 .NET 里对该方法执行 `RuntimeHelpers.PrepareMethod`（强制 JIT 编译），
  9 个相关方法全部通过（原始版/重建版结果相同）。异常表写错时这一步会直接抛
  `InvalidProgramException`——开发过程中正是靠它抓到了外层 `finally` 范围写错的 bug。

### 8.5 边界

- 需要 `InstallPack*` 这些方法体存在；缺失则跳过本项并提示，其余补丁照常。
- 需要 `PackType` 是第 4 个局部变量（`Int32`）且至少有 3 次常量赋值，否则提示版本差异并跳过。
- 不恢复的两处：资源站整合包详情页的一键安装按钮、资源页"安装已有整合包"按钮
  （前者需要新增 MemberRef 行，后者需要新增局部变量签名与字符串常量，都超出"只改代码"的范围）。
